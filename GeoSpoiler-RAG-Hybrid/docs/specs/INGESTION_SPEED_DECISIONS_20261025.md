# Согласованные изменения загрузки материалов

Дата согласования: 25 октября 2026 года.

Область изменений — получение и подготовка новых материалов: `fetch → normalize → enrich → обновление локальных индексов`, а также обсуждаемая отдельно загрузка в LightRAG командой `load`. Решения относятся к скорости заливки материалов. Оптимизация ответов на пользовательские вопросы в этот набор не входит.

Согласованы все шесть пунктов, включая выборочную обработку медиа. Статус решений не означает, что изменения уже реализованы. Остальные замечания первоначального аудита перечислены отдельно в конце документа и не считаются согласованными изменениями.

## Согласованные изменения

### 1 Пропуск лишнего перевода

Уверенно русский текст должен проходить нормализацию без обращения к LLM для перевода. Определение языка выполняется до модельного вызова. Иностранный и смешанный текст сохраняют обработку, необходимую для корректного перевода; украинский текст нельзя считать русским только по наличию кириллицы.

Текущий [переводчик](../../src/geospoiler/ingestion/normalizer/translator.py) отправляет модели любой непустой текст, поручая ей вернуть русский текст без изменений.

### 2 Три одновременных вызова

Разрешить до трёх одновременных LLM-вызовов в одном конвейере. Это общий предел для его операций, использующих тот же LLM-backend, включая перевод и обогащение. Каждый этап не должен получать собственные три дополнительных слота поверх общего предела.

Обогащение должно использовать три рабочих задания, согласованные с ограничителем backend. Начальные целевые значения: `ENRICHMENT_CONCURRENCY=3` и `CODEX_LLM_MAX_CONCURRENCY=3`. Для выполнения общего ограничения при передаче материалов между этапами требуется проверить совместную работу всех вызывающих путей.

### 3 Выборочная обработка медиа

Сначала обрабатывать текст поста. Само наличие вложения не должно запускать его скачивание и анализ. Анализировать вложение, когда из текста видна зависимость содержания от него: данные на скриншоте, сведения на карте, документ либо слова в записи. Для самодостаточного текста без такой зависимости обогащать текст, пропуская предварительную обработку вложений.

| Содержимое поста | Действие по умолчанию |
| --- | --- |
| Самодостаточный текст без зависимости от вложения | Сохранить и обогатить текст, медиа не анализировать |
| Текст явно отсылает к содержанию вложения | Получить и проанализировать нужное вложение, включить извлечённые сведения в карточку |
| Только медиа либо неопределённая подпись без содержательного текста | Для видео, голоса, аудио, документа и изображения с короткой подписью, в которой есть буквы, сохранить привязку к источнику и статус необработанного вложения; автоматический анализ не запускать. Пост «только изображение» скачивать и анализировать всегда, включая каждое изображение альбома |

Пост «только изображение» — пост, все вложения которого являются изображениями, а после удаления ссылок, хештегов и эмодзи в тексте не остаётся букв и цифр. Решение по альбому принимается по общей подписи. Смешанный пост, где кроме изображения есть видео, голос, аудио или документ, обрабатывается прежним выборочным правилом для всех вложений. `MEDIA_PROCESSING_MODE=all` не меняется. Уточнение 29 октября 2026 года (2026-10-29): изображение без подписи — единственный источник смысла поста.

Выбирать необходимые операции: для речи — транскрипцию, для текста на изображении — OCR, для визуальных сведений — соответствующий анализ. Не запускать все способы обработки для каждого вложения.

Решение о необходимости медиа желательно получать локальными правилами или в уже необходимом вызове обогащения текста, без отдельного LLM-запроса на классификацию каждого поста. Это требование к новой реализации: существующий контракт обогащения такого решения пока не содержит. Получение сведений из выбранного вложения может потребовать последующего дополнения карточки.

Для намеренно пропущенных вложений сохранять отдельный статус «вложение не анализировалось», тип медиа и доступную идентификацию источника, включая ссылку на пост. Такой пропуск не считать ошибкой извлечения и не обозначать как доказанную незначимость медиа. Полезный текст поста должен оставаться доступен для поиска.

Принятое ограничение: по подписи нельзя гарантированно определить ценность вложения. Если важные сведения есть только в необработанном медиа, они не участвуют в текстовом поиске. Последующий анализ конкретного вложения по запросу возможен как отдельное развитие; автоматический просмотр всех найденных карточек при каждом вопросе не входит в согласованный режим. Доступность оригинала впоследствии не гарантируется.

Срок хранения файлов, скачанных для выбранного анализа, и политика кеша требуют отдельной настройки. При внедрении сначала проверить выборочный отбор на небольшой реальной выборке пересылаемых постов и оценить пропуски важных вложений.

Текущая реализация ещё не соответствует этому правилу: на момент проверки 25 октября 2026 года рабочая конфигурация давала `MEDIA_CAPTURE_ENABLED=true`, `TRANSCRIPTION_ENABLED=true`, `MEDIA_VISION_BACKEND=luna`. Значение `MEDIA_CAPTURE_MAX_BYTES=0` означает отсутствие ограничения размера. В [Telegram fetcher](../../src/geospoiler/ingestion/fetcher/telegram_client.py) фотографии скачиваются отдельным маршрутом, который не проверяет `MEDIA_CAPTURE_ENABLED`; одного переключения этого флага для нового поведения недостаточно.

### 4 Загрузка графа по изменениям

Обычный `load` должен добавлять новые документы, обновлять изменённые и пропускать неизменившиеся успешно обработанные документы. Совпадающий документ не должен удаляться и вставляться заново только из-за очередного запуска загрузчика.

Проверять нужно состояние обработки и подготовленное содержимое документа, а не только наличие его ID в графе. Неуспешная либо незавершённая загрузка требует повторной обработки. Обновление связанных метаданных источника должно сохраняться и при переиспользовании документа.

Повторную обработку после изменения правил извлечения сущностей и связей, при восстановлении графа или по явному запросу пользователя сохранить отдельным режимом.

Пример: при 1000 уже загруженных неизменившихся материалах и 3 новых на добавление должны поступить только 3 новых. Если один старый материал изменился, его нужно обновить, а остальные совпадающие документы переиспользовать.

Текущий [загрузчик](../../src/geospoiler/retrieval/lightrag/ingest.py) собирает все подходящие карточки из папки, а обычный путь по умолчанию не переиспользует совпадающие документы. Это поведение подлежит изменению. Обычный `run` не вызывает `load`; решение относится именно к явной загрузке графа.

### 5 Передача материала сразу после нормализации

Готовый нормализованный материал должен поступать в обогащение сразу, без ожидания нормализации всей партии. Скачивание и нормализация следующих материалов могут продолжаться, пока предыдущие уже обогащаются.

При реализации необходимо сохранить целостность и возможность продолжить работу после сбоя:

- Передавать задание только после полного сохранения и проверки текста вместе с метаданными.
- Ограничивать очередь, чтобы нормализация не создавала неограниченное число ожидающих заданий.
- Сохранять прогресс через одного координатора, исключая конфликтующие записи состояния.
- Продвигать чекпойнты с учётом незавершённых материалов, чтобы поздний успешный результат не скрыл более ранний сбой.
- Согласованно обновлять локальные индексы по готовым результатам.

В текущем [полном запуске](../../src/geospoiler/cli/pipeline.py) все материалы сначала скачиваются, затем нормализуются, затем запускается обогащение. Команда `load` остаётся отдельной операцией; решение по пункту 5 не добавляет автоматическую загрузку графа.

### 6 Независимость готовой карточки от смены модели

Смена LLM, профиля backend или уровня рассуждений сама по себе не должна вызывать повторное обогащение готовой валидной карточки. Новая модель применяется к новым заданиям. Название модели и уровень рассуждений сохраняются в метаданных как происхождение результата.

Это правило актуальности на случай будущего самостоятельного изменения настроек пользователем. Оно не поручает менять текущую Luna, профиль `luna` или `xhigh` в рамках этой работы.

Основания для повторного обогащения:

- изменился исходный материал или значимые входные метаданные;
- изменились правила извлечения, обязательная схема либо контракт обработки;
- результат отсутствует, повреждён, невалиден или предыдущая обработка не завершилась успешно;
- пользователь явно запросил принудительную переработку.

Это правило должно одинаково действовать для обычных карточек и YouTube-карточек с сегментами. Согласованность уже сохранённой YouTube-генерации и её внутренних метаданных должна сохраняться.

Текущая [проверка смены модели](../../src/geospoiler/providers/llm_backend.py) инвалидирует результат при смене модели одного backend даже с `REGENERATE_ON_PROFILE_CHANGE=false`. Это поведение подлежит изменению.

### Объём контекста при ответах

При локальной сборке контекста из FTS карточек и YouTube, без графового канала и без нового вызова LLM, аудит 25 октября 2026 года получил 52–98 тысяч оценочных входных токенов на вопрос. В одном случае три видеоматериала дали около 53 тысяч токенов. Это оценка подготовленного входа, а не фактический учёт провайдера и не количество токенов сгенерированного ответа.

[Упаковка контекста](../../src/geospoiler/answering/late_fusion.py) может включать транскрипт, события, тезисы, ключевые пункты и summary одного источника. Пользователь отдельно спросил о риске ухудшения ответа. Гарантии сохранения качества без сравнения нет; снижение числа токенов само по себе не считается успехом.

Повторная проверка кода показала, что [удаление совпадающих блоков](../../src/geospoiler/answering/late_fusion.py) уже реализовано функцией `_deduplicate_block_items`, которую вызывает `_source_block_items`. Сравнивается `dedupe_value` с нормализацией пробелов и регистра внутри источника. Предлагать это как новую оптимизацию было ошибкой. Наличие этой функции не доказывает отсутствия всех повторов; дополнительный полезный резерв без потери сведений пока не установлен.

Пользователь прямо отклонил более сильное сокращение содержания видео и постов из-за потери сведений. Не вводить новый отбор коротких фрагментов, сокращение числа источников или уменьшенный бюджет ради экономии токенов в рамках этих договорённостей.

Текущую упаковку контекста оставить без новых изменений. Ранее предложенный ориентир 20–30 тысяч токенов снять с плана. Уже существующие защитные пределы контекстного окна этим решением не изменяются. Большой объём входа остаётся наблюдением, а не основанием сокращать материалы вопреки требованию полноты.

### Уточнения о графе и подтверждении ответа

Пользователь пояснил, что граф намеренно не обновлялся после тестового удаления поста. Текущее рассогласование считать состоянием тестовой базы, а не установленной причиной для срочного исправления. Автоматическое обновление или восстановление графа сейчас не запрошено. Ранее измеренное отличие 130 из 131 документов остаётся наблюдением снимка; его причину не следует автоматически сводить к удалению одного поста. Согласованная политика обычного `load` из пункта 4 сохраняется.

Требование пользователя к ответу — подтверждение утверждений содержимым поста. Проверка истинности исходного поста по внешним источникам не требуется. Предлагаемый критерий: если в ответе названы сумма, дата, участник или причинная связь, указанный пост должен содержать соответствующее основание; авторское предположение нельзя незаметно превращать в установленный факт. Отдельный LLM-валидатор для каждого ответа и расширенная система оценки цитирования не согласованы.

Проверка `_build_messages` подтвердила, что действующий prompt уже требует отвечать только по переданному контексту, различать факт, заявление, план, прогноз и предположение, ставить ссылки рядом с поддержанными утверждениями. Замечание первоначального аудита относилось к границе автоматической проверки ID и URL, а не к доказанному случаю неподтверждённого ответа. Текущее предложение — оставить эти правила и действующую проверку ссылок без нового модуля, дополнительного LLM-вызова или отдельной кампании оценки цитирования. Новая доработка по этому пункту не утверждена.

### Что означают тайминги

Пользователь уточнил, что время этапов уже можно посмотреть. Повторная проверка подтвердила существующие измерения:

- В [Late Fusion](../../src/geospoiler/answering/late_fusion.py) функция `_timed_retrieval_channel` записывает `duration_ms` отдельно для LightRAG, FTS карточек и FTS YouTube в `channel_statuses`.
- [Проверочный smoke](../../src/geospoiler/operations/late_fusion_activation_smoke.py) сохраняет эти значения; у попытки полного прогона есть `started_at` и `finished_at`.
- [Транскрипция](../../src/geospoiler/ingestion/normalizer/transcription_handler.py) сохраняет `latency_ms`, включая сведения о попытках обработки.

Неверно описывать проект как не имеющий замеров. При этом перечисленное не даёт полной разбивки обычного вопроса на чтение карточек, упаковку контекста, ожидание слота backend и сам вызов синтеза. Сначала использовать имеющиеся показатели. Добавление недостающих замеров отложить до конкретной диагностической необходимости; отдельная реализация не согласована. Внутреннее время рассуждений модели нельзя точно отделить, если backend не предоставляет такие данные.

При запуске `/setup-matt-pocock-skills` пользователь подтвердил создание нового приватного `kovr33k/geospoiler-rag` для трекера, без переноса кода и архивации прежних репозиториев на этом шаге. Репозиторий создан; удаление старых не запрошено.

План переноса: новый приватный репозиторий с основной веткой `main`, актуальным исходным кодом и документацией из рабочей копии, без переноса старой Git-истории и рабочих баз данных. Сначала проверить состав нового снимка и настроить один CI для актуального дерева: полный offline pytest, блокирующий Ruff, проверку Windows и Linux. После подтверждения переноса старые репозитории оставить архивами, сохранив доступ к истории; удаление не является необходимым этапом. Новый tracker уже создан, но исходный снимок, CI и изменение remotes пока не выполнены.

На основе договорённостей подготовлена [спецификация](RAG_INGESTION_AND_GITHUB_SPEC_20261025.md) по шаблону `$to-spec` и опубликована в [issue №1](https://github.com/kovr33k/geospoiler-rag/issues/1) с меткой `ready-for-agent`. Границы тестирования через `run` и `load` с управляемыми внешними ответами подтверждены пользователем 25 октября 2026 года. Настройка `/setup-matt-pocock-skills` завершена: пользователь выбрал корневой `AGENTS.md` и подтвердил [показанный проект настроек](AGENT_SKILLS_SETUP_DRAFT_20261025.md). Правила tracker и доменных документов записаны, метка `ready-for-agent` создана. Опубликованный текст сверён с локальной спецификацией. Публикация не означает реализации конвейера.

Достоверность smoke также должна относиться к повседневному режиму запросов. Создание нового репозитория само по себе не устраняет ограничение запуска Actions на уровне учётной записи.

Свежая проверка [последнего CI приватного репозитория](https://github.com/kovr33k/geospoiler-rag-hybrid-backup/actions/runs/40063519906) показала ноль выполненных шагов. Аннотация GitHub указывает на проблему оплаты или лимита расходов учётной записи. Это отдельное условие запуска Actions; перестройка workflow сама его не устраняет. Учётные платежные настройки не менялись.
