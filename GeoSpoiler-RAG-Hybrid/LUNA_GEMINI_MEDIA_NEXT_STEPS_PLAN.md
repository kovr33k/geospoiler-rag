# План закрытия пилота Luna + Gemini Media

## Цель

Довести оставшиеся три пилотные карточки (`Балтийские страны/4`, `Ультра левые и ультра правые/16`, `Ультра левые и ультра правые/18`) до состояния, в котором их можно безопасно заменить в рабочем корпусе и загрузить в RAG без потери смыслов, ложных флагов и дублей. `Китай/6` и `Китай/72` исключены по решению пользователя после удаления постов в Telegram.

## Текущее решение по пилоту

- Все 3 оставшиеся карточки структурно валидны и загружены в LightRAG.
- Существенных выдуманных фактов при ручном сравнении с caption, OCR, визуальным описанием и транскриптом не обнаружено.
- Китайские источники удалены из active output, state, FTS и registry; архив оставлен отдельно для обратимого аудита.

## Этап 1. Исправить сборку graph_text

1. Заменить текущую постобработку, которая делает `graph_text.replace(quote_text, "")`, на безопасное удаление только foreign/Ukrainian verbatim-цитат вместе с парными кавычками.
2. Не добавлять отдельный раздел цитат в `graph_text`; русские смысловые формулировки, уже использованные Luna внутри summary, events или theses, сохранять.
3. Добавить регрессионные тесты для русских и иностранных цитат, вложенных кавычек и частичных совпадений.
4. Ввести автоматический инвариант: в `graph_text` запрещены пустые `«»`, `“”`, `""` и двойные пробелы после удаления текста.

Критерий готовности: у всех трёх активных карточек ключевые термины сохраняются, пустых кавычек нет, существующие тесты проходят.

## Этап 2. Сделать technical quality flags детерминированными

1. Запретить generic LLM самостоятельно назначать pipeline-флаги, как минимум:
   - `contains_legacy_media_placeholders`;
   - `transcript_unavailable`;
   - `timestamps_unavailable`;
   - `partial_segment_failure`;
   - `extraction_unstable`.
2. Вычислять эти флаги только из реального результата media pipeline и его metadata.
3. Не считать канонический заголовок `[Video transcript | artifact=...]` признаком необработанного media: это служебная граница успешно приложенного транскрипта.
4. Оставлять `possible_duplicate` только при подтверждении отдельным детектором дублей, а не из-за повторяющегося OCR соседних кадров.
5. Добавить тесты, которые подтверждают одинаковые флаги для одинакового технического состояния независимо от ответа Luna.

Критерий готовности: у трёх активных карточек нет ложных runtime-owned флагов; отсутствие таймкодов отражается только по определенному контракту pipeline.

## Этап 3. Повторно собрать и принять три активные карточки

1. Использовать сохраненные normalized-входы трёх оставшихся источников без повторного скачивания media.
2. Повторно построить enriched-карточки после исправлений этапов 1 и 2.
3. Выполнить структурную проверку и ручную смысловую проверку по четырем слоям: caption, OCR/vision, audio transcript, итоговая карточка.
4. Проверить отдельно:
   - отсутствие неподтвержденных имен, событий и причинно-следственных связей;
   - сохранение разницы между утверждением автора, цитатой героя и наблюдаемым изображением;
   - маркировку низконадежного фонетического/шумного транскрипта;
   - отсутствие пустых цитат и ложных quality flags.
5. Сформировать manifest с `source_id`, путями, SHA-256 normalized/enriched/graph_text и итогом приемки каждой карточки.

Критерий готовности: 3/3 активные карточки проходят структурную и смысловую приемку.

## Этап 4. Безопасно заменить карточки в рабочем корпусе

1. Сохранить резервную копию текущих production normalized/enriched-файлов этих трёх сообщений и состояния индекса.
2. Перенести принятые normalized-артефакты в штатные production-пути.
3. Создать финальные enriched-карточки с provenance, указывающим на production normalized, а не на каталог пилота.
4. Проверить уникальность `source_id` и отсутствие второй версии той же карточки в корпусе.

Критерий готовности: в production лежит ровно одна принятая версия каждого из трёх источников, восстановление старой версии возможно из backup.

## Этап 5. Точечная загрузка в RAG и проверка

1. Загрузить только manifest трёх принятых карточек в режиме replace/upsert, не весь корпус.
2. Перестроить необходимые FTS/registry представления.
3. Проверить, что для каждого `source_id` существует ровно один документ и его актуальные `graph_text`/`search_text` доступны поиску.
4. Выполнить контрольные запросы на характерные смыслы каждой карточки, включая иностранные лозунги `Ультра/16` и формулировку про политическую волю НАТО из `Балтийские страны/4`.
5. Проверить Late-Fusion, URL источника и citations; legacy fallback не должен скрывать отсутствие пилотной карточки.

Критерий готовности: три карточки находятся ожидаемыми запросами, citations ведут на правильные Telegram URL, дублей и незаметного fallback нет.

## Этап 6. Продолжение массовой обработки

1. Запустить малый canary на 10–20 разнородных сообщениях: текст, фото, Telegram video, Instagram Reel, длинное видео и шумный звук.
2. Принять canary теми же автоматическими и ручными критериями.
3. Только после успешного canary запускать оставшийся массив пакетами с checkpoint/resume и журналом ошибок.
4. После каждого пакета контролировать долю недоступных media, ошибки transcription/vision, ложные флаги, пустой `graph_text`, дубли и стоимость/latency.

## Порядок исполнения

Этапы 1–5 для трёх активных карточек уже выполнены. Массовое продолжение разрешать только после canary этапа 6.
